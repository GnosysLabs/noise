# Noise relays

## Managed signed release

Relay releases are independent and use tags `relay-vX.Y.Z`. Follow `docs/RELAY_RELEASES.md` and inspect `.github/workflows/relay-packages.yml` immediately before release.

1. Update `crates/noise-relay/Cargo.toml` and `Cargo.lock`.
2. Commit and push the accepted relay source.
3. With explicit authorization, create and push `relay-vX.Y.Z`.
4. Wait for both amd64 and arm64 `.deb` files in the draft GitHub release.
5. Sign and publish:

```sh
scripts/promote-relay-release.sh relay-vX.Y.Z stable
```

The release private key defaults to `~/.config/noise/relay-release.pem`, must remain mode `600`, and must never be printed or committed. The script verifies the signature against `deploy/relay-release-public.pem`, publishes the release with `latest=false`, and writes:

- `deploy/relay-channels/stable.json`
- `deploy/relay-channels/stable.json.sig`

Inspect, commit, and push those exact generated bytes after promotion.

## Production service

Read [servers.md](servers.md) before connecting or deploying. It documents both live hosts, their different SSH users, staging, backups, verification, and rollback.

The primary relay is `https://noiserelay.gnosyslabs.xyz` on `cyphers-vps`, normally:

- binary: `/usr/bin/noise-relay`
- config: `/etc/noise-relay/config.toml`
- service: `noise-relay.service`

Use the `cyphers-vps-ssh` skill for live access. Prefer the signed package/channel updater. Use a direct binary hotfix only when the user explicitly authorizes that path.

For a direct x86-64 Ubuntu hotfix from macOS, the established cross-build is:

```sh
cargo zigbuild --release -p noise-relay --target x86_64-unknown-linux-gnu.2.35
```

Before replacement:

1. Verify the exact remote host/service/config/binary paths.
2. Run `ldd` on the staged binary and require no missing library.
3. Back up the existing binary and config to explicit timestamped paths.
4. Preserve owner, group, mode, environment files, data directory, and secrets.
5. Install the staged binary atomically, restart the service, and retain the rollback commands.

## APNs

The relay APNs block uses:

```toml
[push_notifications]
key_file = "/etc/noise-relay/AuthKey_HFYLVC3UAG.p8"
key_id = "HFYLVC3UAG"
team_id = "4PDUNTF69S"
topic = "xyz.gnosyslabs.noise.ios"
```

The key file must be owned for the relay service and readable only as required; never print or copy its contents through chat/logs.

## OHTTP compatibility

When adding a relay route, update both the public route and the private OHTTP request allowlist/dispatcher in `crates/noise-relay/src/main.rs`. Otherwise browser/native clients may receive `404 unsupported private relay request` even while the public endpoint exists.

## Member admission capability

Clients let any group member admit a pending join instead of waiting for the founder, but only once **every** relay in the client's pinned list answers `GET /v2/relay-capabilities` with `member_admission: true`. Older relays reject member-authored epochs, so until the whole set is upgraded, admission silently falls back to founder-only and joins wait again.

The shipped default list includes a relay this project does not operate (`noiserelay.irisirc.chat`). Confirm its capability response after upgrading `noiserelay.gnosyslabs.xyz`, or member admission stays off for every default client:

```sh
curl -s https://noiserelay.gnosyslabs.xyz/v2/relay-capabilities
curl -s https://noiserelay.irisirc.chat/v2/relay-capabilities
```

## Verify

- Require `systemctl is-active noise-relay.service`.
- Inspect current-boot journal lines for panics, restart loops, config errors, and APNs errors.
- Verify the relay’s localhost `/health`.
- Verify `https://noiserelay.gnosyslabs.xyz/health`.
- Confirm reported software/protocol versions match the intended build.
- Exercise the client action that required the relay change.

If a live check fails, restore the prior binary/config or prior signed channel rather than improvising further changes in production.
